# Architecture decision records

Statuses distinguish user agreement from engineering proposal. No ADR is proof of implementation.

| ADR | Status | Subject |
|---|---|---|
| [0001](0001_VISION_AND_LEARNING.md) | Accepted by explicit user instruction | Vision and learning-first portfolio priority |
| [0002](0002_DYNAMIC_CONFIGURATIONS.md) | Accepted principle; proposed mechanics | Dynamic configurations from a bounded tool catalog |
| [0003](0003_STACK_AND_CLOUD.md) | Proposed default | Stack, local adapters and Azure target |
| [0004](0004_STAGED_TEXT_AND_VOICE.md) | Accepted sequence; proposed mechanics | Text first and voice-first destination |
| [0005](0005_REPOSITORY_CONTINUITY.md) | Accepted by explicit user instruction | Repository files and Git as continuity mechanism |

For a new ADR use the next stable number. Include date, status, context, decision, alternatives, consequences, affected files/tasks and supersedes/superseded_by. Preserve old ADRs and update the decision register. An implemented default can be marked adopted with evidence; do not retroactively say the user agreed earlier.
